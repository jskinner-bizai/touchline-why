# Touchline Why

## One-line description

A broadcast explanation desk that connects a synthetic football moment to its evidence and withdraws stale output when the facts change.

## Short pitch

Broadcast explanations need to stay useful when an event arrives late, a statistic changes, or a model fails. Touchline Why gives a producer a visible chain from match event to published overlay.

The demo follows two fictional clubs. Exact event-time statistics generate candidate patterns. In the recorded model experiment, Microsoft Agent Framework with its Ollama provider asked one local model to select a candidate ID. Deterministic code validated the choice and supplied every number, evidence reference and sentence. The shipped demo replays the two accepted historical outputs with clear labels; it makes no live model request.

A producer can inspect the source events, switch between a short fan summary and an analyst view with window and interpretation limits in English or Spanish, correct a recorded goal, and see the prior overlay retracted. A declared timeout returns verified facts. Reopening the saved replay restores committed facts and revisions while discarding the old selected insight. The final recap separates the corrected score from historical model selections.

The current candidate also replays a separate clause-review experiment: a model suggests which parts of producer copy to keep or remove, with evidence. Approval creates a clearly labeled draft. A fact, revision or view change invalidates that draft. Correction explanations come directly from the ledger; they do not replace the captured model reason. No copy is transmitted by this workflow.

The intended use is a producer reviewing explanations before they reach viewers. This is a bounded synthetic prototype, with no live match feed, cloud deployment, multi-agent claim or measured real-world audience outcome.

## Microsoft technologies used

Microsoft Agent Framework core 1.22.0 and its Ollama provider 1.0.0b261015 executed the historical local candidate-selection experiment. One SDK Agent chose an allowed ID; it did not calculate match facts or write free-form commentary. Two accepted outputs concern one moment, alongside two client timeouts. The current default replays the preserved receipts. No Azure, Foundry, MCP, multi-agent execution or current live model benefit is claimed. The optional current inference route has mock coverage only.

The separate four-call claim-review trial used those same Microsoft SDK components and cached `gemma4:12b`. Three of four strict cases passed. All four selected the expected clauses and evidence, but one failed to distinguish an approved correction from a generic contradiction. The unchanged original NO_GO and all four receipts are retained. Supported-clause retention and a specific causal warning were useful candidates beyond generic manual review, without a measured producer benefit or general accuracy estimate. The current candidate replays this advice with explicit recorded labels; it makes no new model request.

## Proposed adoption path

Today: a local single-operator desk, one fictional fixture, versioned overlay output, evidence/revision checks and a bounded SQLite command journal. The included tests exercise corrections, stale output and process-crash boundaries. There is no production feed, authentication, multi-operator access, tenant isolation or production monitoring.

Proposed pilot: map one licensed data feed into the existing event/revision contract, connect the overlay JSON to a broadcast graphics sandbox, and measure correction propagation, stale-card duration, operator task time and evidence accuracy. A deployment design would need authenticated operator roles, audit export, concurrent-edit policy, retention, monitoring and recovery objectives before use by a broadcaster.

Proposed Microsoft deployment: evaluate an Azure-hosted selector with Agent Framework and an appropriate durable event store, while retaining deterministic publication gates. Provider choice, data residency, costs, access controls and failover require design and approval. This is a path to evaluate, not an implemented cloud integration or deployment commitment.
